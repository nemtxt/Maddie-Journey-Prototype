# Maddie Journey V4.3 — Employee Profiles & Division Dashboard Refinement

**Status:** Integrated into the existing read-only fictional-data prototype on `main`.

## Purpose

Make each employee profile and division dashboard easier to understand without changing the source dataset, passcode workflow, routes, original navigation, 3D Office, V4.1 data-driven charts, V4.2 tables or connected record destinations.

## Implementation files

- `maddie-v43-profiles-divisions.js`: Adds source-derived employee snapshots and recorded career milestones, makes detailed information groups collapsible, and applies division-specific page hierarchy.
- `maddie-v43-profiles-divisions.css`: One monochrome, responsive profile and division design layer, loaded after V4.2.
- `p-main-demo.js`: The existing profile template receives only a stable `data-mj-v43-employee` identifier to associate each open modal with its exact fictional record.
- `tests/v43-profile-division-contract.js`: Dependency-free DOM and fixture verification.

## Employee profile changes

1. **Identity header:** Original avatar, name and role stay intact. Added employment status, Level 1–6 when recorded, and a direct link to the corresponding division.
2. **Four-signal profile snapshot:** employment status with tenure, 201-file completion with source document counts, recorded 30-day late events, and count of associated case entries.
3. **Career timeline:** shows recorded hire and regularization dates in chronological order. Current journey stage and any development tracker status are clearly marked as **undated**. No promotion, salary-change or review date is invented.
4. **Information hierarchy:** prioritizes Employment, Attendance/201-file, and 201 Documents; remaining sections follow as Contact, Government IDs, Compensation, Cases, and other existing content.
5. **Progressive disclosure:** Employment, Attendance and 201 Documents initially open; contact/government/compensation/cases groups can be expanded on demand. Profile details are not deleted and remain available with **Expand all details**.
6. **Navigation:** the existing profile jump chips now follow the revised information order. Jumping to a collapsed group expands it before scrolling.
7. **Source masking:** original sensitive-value masking, link destinations, document status components and backend-derived values remain untouched. The new summary does not repeat phone numbers, payroll amounts, government identifiers or private addresses.
8. **Appearance:** black/white surfaces, dark readable text on light background and high-contrast text on dark background. Division colors appear only as identity indicators.

## Division dashboard changes

- A standardized heading and subtle division-color border match the company organization chart.
- Compact department context communicates recorded level coverage and employment-status counts without adding another large KPI-card grid.
- Existing division org-chart content is retained; its heading is standardized to **Organization structure**.
- At a glance, People, Tasks, Weekly Pulse, Journey Stages and Other Divisions receive consistent headings, spacing and card treatments.
- The Other Divisions section becomes a compact, responsive directory of existing division links.
- V4.1 division intelligence and V4.2 table paging/search/filtering are preserved.
- All company color mappings continue to use `window.MJ_DIVISION_COLOR`, whose established division palette remains the source of truth.

## Data contract and privacy

- The fictional roster contains **51 unique employees across eight divisions**.
- Employee profile identifiers use the existing `EMP[].i` index; the enhancement does not guess by name.
- Source dates are included only when they validate as exact ISO calendar dates. Missing event dates stay undated.
- Derived division averages are simple arithmetic means of existing `EMP[].f`; lates are recorded counts from `EMP[].l30`.
- Case counts are derived from `MCD.CASES[].people[].i`.
- No records, permissions, connectors, salaries, government IDs, contact details or persisted settings are written.

## Regression contract

**Automated checks:**

- 26/26 DOM and fixture contract tests passed for employee profile details, timeline, navigation, collapse/expand controls, division header context and division chart changes.
- All 51 profile records resolve by exact employee ID.
- All eight division counts sum to 51; all division 201-file averages reconcile.
- Original profile fields, masking and case arrays are not rewritten.
- Script syntax, CSS structure and entry-file asset synchronization are checked before release.

**Manual checks still required:**

- Rendered mobile and desktop profile geometry, especially the close button and very long fields.
- Keyboard navigation and screen-reader reading order with real browser accessibility tools.
- Division charts, V4.2 tables and profile jumps after rapid route switching.
- Both light and dark appearances across real viewport sizes.

These are source/DOM tests; they do **not** constitute full live-browser or device testing.
